Setting up Secure Boot, step by step

Take one board from “runs anything” to cryptographically locked — three stages, real commands, and exactly what each one prints on the wire. Every step is verified against the local ESP-IDF v6.0.1 documentation. Stages 1–2 are fully reversible; Stage 3 burns eFuses forever.

⚠️

Read before Stage 3. Enabling hardware Secure Boot burns one-time-programmable eFuses. There is no undo, no factory reset. A locked board runs only images signed with your key — lose the key and it can never be updated again. Do Stage 3 on a sacrificial dev board only, never a production device.

Stage 1. Baseline — see an unprotected device

Goal: flash the demo as-is and confirm it reports Secure Boot DISABLED. No keys, no eFuses.

✓ reversible

The shipped sdkconfig.defaults produces an ordinary, unsigned firmware. Build and flash it, then open the serial monitor:

$ idf.py set-target esp32c5     # once per checkout
$ idf.py build
$ idf.py -p COM15 flash monitor  # exit monitor: Ctrl-]

Under the hood

The app never trusts a compile-time flag. esp_secure_boot_enabled() queries the actual SECURE_BOOT_EN eFuse over the eFuse controller, so the “DISABLED” you see is ground truth, not a setting.

Stage 2. Sign the app — software only

Goal: rehearse the whole signing workflow without touching eFuses. The app gets a real signature; the hardware stays unlocked.

✓ reversible

1 — Generate an ECDSA-256 signing key

This private key is the root of trust for every device that will trust it. Keep it secret; it is git-ignored (*.pem) in this project.

$ idf.py secure-generate-signing-key --scheme ecdsa256 secure_boot_signing_key.pem

2 — Turn on signed-app verification (no eFuse burn)

Uncomment the Stage 2 block in sdkconfig.defaults, or set it in menuconfig → Security features. Either way these three keys are what matter:

CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT=y
CONFIG_SECURE_SIGNED_APPS_ECDSA_V2_SCHEME=y
CONFIG_SECURE_BOOT_ECDSA_KEY_LEN_256_BITS=y
CONFIG_SECURE_BOOT_SIGNING_KEY="secure_boot_signing_key.pem"
$ idf.py fullclean && idf.py build   # fullclean: re-apply the new defaults
$ idf.py -p COM15 flash monitor

3 — Inspect the signature that was appended

$ espsecure signature-info-v2 build/secure_boot_demo.bin

Under the hood

A 1216-byte signature block is now appended to the app: the public key, an ECDSA-P256 signature over the image hash, and a CRC. A running app could verify an OTA against it — but with no eFuse digest, the hardware still boots anything.

Stage 3. Lock the hardware — Secure Boot v2

Goal: burn the eFuses so the ROM enforces the chain of trust on every boot. This cannot be undone.

✖ irreversible

One-way door ahead

The steps below burn SECURE_BOOT_EN and a key digest permanently. Only continue on a board you are willing to lock forever, with your signing key safely backed up.

1 — Configure Security features in menuconfig

$ idf.py menuconfig   # → Security features

2 — Build the signed bootloader, then flash it by hand

Secure Boot bootloaders are not flashed by idf.py flash — the build prints the exact esptool write-flash command for you to run.

$ idf.py bootloader

3 — Flash the partition table + app, then let it boot

$ idf.py -p COM15 flash monitor   # flashes partition-table + app, NOT the bootloader

On the first boot, the second-stage bootloader verifies the images, then burns the eFuses. Watch it happen:

4 — Verify what got burned

$ idf.py -p COM15 efuse-summary

The same result, done explicitly with espsecure + espefuse (useful for external provisioning / a signing server). Order matters.

$ espsecure generate-signing-key --version 2 --scheme ecdsa256 secure_boot_signing_key.pem
$ espsecure digest-sbv2-public-key --keyfile secure_boot_signing_key.pem --output digest.bin
$ espefuse --port COM15 --chip esp32c5 burn-key BLOCK_KEY0 digest.bin SECURE_BOOT_DIGEST0
$ espefuse --port COM15 --chip esp32c5 burn-efuse SECURE_BOOT_EN
  • BLOCK_KEY0 is any free key block (0–5); the C5 has 3 digest slots for rotation/revocation.
  • Using ECDSA-P384 instead? Also burn SECURE_BOOT_SHA384_EN (image hashing moves to SHA-384).
  • Production hardening: also burn DIS_PAD_JTAG, DIS_USB_JTAG, DIS_DIRECT_BOOT, and SECURE_BOOT_AGGRESSIVE_REVOKE.

The whole pipeline, as data flow

Recommended companion — Flash Encryption

Secure Boot proves authenticity (only your code runs). It does not stop someone reading firmware/keys out of flash. For production, enable Flash Encryption in the same menuconfig (mode Development while iterating, Release for the field) so the flash is also confidential — together they close the flash-swap (TOCTOU) gap.

Life after the lock

  • Every future bootloader/app/OTA must be signed with a key matching the burned digest.
  • The USB-OTG ROM download stack is disabled; JTAG and UART download are locked per your menuconfig choices.
  • Further eFuse read-protection is disabled by default (to keep the public-key digest readable).
  • Lose the signing key → the board can never be updated again. Back it up offline; for production, generate it on an HSM.

Stage 4. Encrypt the flash — the production companion

Goal: make the flash confidential, not just authentic. Secure Boot stops tampering; Flash Encryption stops readout. Production wants both.

✖ irreversible
⚠️

Also a one-way door. Enabling Flash Encryption burns eFuses and generates an AES-XTS key locked inside the chip (read-protected, it never leaves). Enable it in the same menuconfig pass as Stage 3. Spare board only.

Flash Encryption transparently encrypts the bootloader, app, and every partition marked encrypted with a per-device AES-XTS key. Firmware is flashed as plaintext and encrypted in place on the first boot; from then on a raw flash dump yields only ciphertext.

1 — Enable it alongside Secure Boot in menuconfig

2 — Flash plaintext once; the first boot encrypts in place

$ idf.py -p COM15 flash monitor

3 — Re-flashing after encryption

In development mode, encrypt-and-flash in one step (plain idf.py flash would write unusable plaintext):

$ idf.py -p COM15 encrypted-flash monitor   # encrypts, then flashes

In release mode the UART bootloader can no longer encrypt — new plaintext firmware arrives only via OTA, which encrypts each image before writing it to flash.

Do not interrupt power

During the first-boot encryption pass, cutting power corrupts the flash and you must re-flash plaintext data and let it encrypt again (this does not count toward any re-flash limit). Let it finish.

Reality check. Recovering a “bricked” board

“Bricked” usually means can’t update, not dead — a locked board keeps running its last valid signed image. What you can recover comes down to two questions: do you still have the key, and is a download path still open?

What went wrongRecoverable?How
Flashed an unsigned / wrong-key app (Secure Boot on)Yes *Re-flash a correctly-signed image with the original key. * if serial download is still open
Lost the signing key (Secure Boot on)No (updates)The board keeps running its current signed app, but no new firmware can ever be accepted
Plaintext flashed to an encrypted device — dev modeYesidf.py encrypted-flash, or disable flash encryption in menuconfig and re-flash
Plaintext flashed — release modeOTA onlyNo serial plaintext path remains; needs a still-working app to OTA a fixed image
Power lost during the first-boot encryption passYes (dev)Re-flash unencrypted data again; this does not count toward the re-flash limit
UART/USB download permanently disabled + a bad imageNoNo serial recovery path is left — this is the genuinely unrecoverable case

The two genuinely unrecoverable combinations

Lost key → you can never sign a new image, so the board is frozen on its current firmware forever. Download mode permanently disabled + a bad image → no serial path remains to push a corrected image. Everything else has a way back.

Prevention checklist — before you touch Stage 3 or 4

  • Back up the signing key offline (two air-gapped copies). It is the one thing that can never be regenerated.
  • While iterating, stay in Flash Encryption Development mode and leave UART download enabled — both keep a recovery path open.
  • Use a “reflashable” Secure Boot digest if you may need to re-flash a signed bootloader on an encrypted device.
  • Provision multiple key digests (the C5 has 3 slots) so a leaked key can be revoked instead of bricking the fleet.
  • Never interrupt power during the first-boot Secure Boot / encryption pass.
  • Prove the whole flow on a sacrificial board before touching anything you care about.
